# LLM 위키 설계

안드레 카파시의 'LLM Wiki' 방식([원문 gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f))을 키트 확장으로 만든 설계입니다. 쓰는 법은 [README 6장](../README.md#llm-위키-wiki).

## 원안
- **세 층**: 원본(raw, 읽기만) → LLM 이 쓰고 고치는 위키(마크다운, 서로 링크) → 스키마(위키의 규칙 문서).
- **세 작업**: ingest(원본 하나를 읽고 요약 페이지를 쓰고 관련 페이지 10~15개를 고침), query(목록부터 보고 답, 좋은 답은 다시 위키로), lint(모순·낡은 주장·고아 페이지·빠진 링크 점검).
- **특별한 파일**: index.md(분류별 목록, 한 줄 요약), log.md(시간순 기록, `## [날짜] 작업 | 제목`).
- 지식을 질문마다 다시 찾는 대신 한 번 정리해 쌓아 간다 (RAG 와 다른 점).

## 이 키트에서 다른 점과 그 까닭
| 제약 | 설계 |
|---|---|
| 도구 한 번이 Copilot·사내AI 대화 한 번 (화면 조작이라 느리고 사용량 제한에 잡힘) | 목록·기록 고치기와 기계적 점검은 확장의 코드가 함. 모델은 여러 페이지를 한 번에 읽고 쓰는 도구를 씀 |
| 도구 결과 6000자, 메시지 10000자 | 검색 결과 2500자, 여러 쪽 읽기 5500자 안. 긴 원본은 offset 으로 이어 읽기 |
| 긴 마크다운을 JSON 문자열로 쓰면 이스케이프를 자주 틀림 | 중계 서버의 `@tool <도구> 이름=값` + 여러 줄 글 형식 (도구 정의의 `text` 인자로). 한 블록에 여러 페이지 (`=== 경로` 줄로 나눔) |
| 웹 검색·외부 패키지 없음 | 검색은 확장 안에서 (단어 + 한글 두 글자 조각, BM25 비슷한 점수). lint 의 '빈 곳 채우기' 는 찾아볼 원본 제안으로 |
| 사내AI 의 개인정보 확인 | 피하지 않음. 위키 내용은 모델이 찾거나 읽을 때만 감 (매 요청 자동 첨부 없음) |
| jupyter 모드 (명령·파일이 노트북) | 위키는 PC 폴더. 위키 도구는 모드와 상관없이 PC 파일을 씀 |

## 정한 것 (2026-10-14)
- 위치: 개인 PC 폴더가 기본(`~/pi-wiki/<이름>`), `/wiki init 이름 폴더` 로 지정 가능
- 보기: Obsidian (링크는 `[[페이지 제목]]`, 파일 이름 = 제목)
- git: 쓰지 않음. 고치기 전 페이지는 `.history/<날짜>/` 에
- 원본 반영에 쓰는 모델: Copilot
- 첫 위키 주제: 모델 운영 (WIKI.md 초안의 분류: 개요, 모델, 파이프라인·작업, 데이터, 지표, 운영 절차, 장애·이슈, 결정, 개념, 원본 요약, 질문 답)
- 모델이 위키를 알아서 씀 (`auto: write`): 주제에 맞는 질문이면 먼저 찾고, 새로 확인한 것은 끝내기 전에 남김

## 구성
| 구성 | 위치 | 내용 |
|---|---|---|
| 확장 `wiki.ts` | profiles/common/agent-template/extensions (키트 확장, 업데이트 때 바뀜) | 도구 3개, `/wiki` 명령, 위키가 켜졌을 때만 도구와 규칙을 모델에게 보임 |
| 스킬 `llm-wiki` | skills/llm-wiki | ingest·query·lint 순서, wiki_write 형식 |
| `WIKI.md` | 각 위키 폴더 (`/wiki init` 이 초안을 씀, 업데이트로 안 바뀜) | 주제, 분류, 페이지 규칙, 작업 |
| 설정 | `~/.pi/agent/wiki.json` | `wikis`(이름→폴더), `active`, `auto`(write·ask·search·off) |

도구:
- `wiki_search(query, limit)`: [[제목]]·경로·요약·맞은 줄
- `wiki_read(path | paths, offset, limit)`: 위키 안 경로 또는 페이지 제목, 여러 개를 한 번에
- `wiki_write(text, op, title)`: `pages/` 아래만, 머리말(title·summary·type) 필수, 새 페이지는 파일 이름 = 제목, 다른 폴더에 같은 이름이 있으면 거절, `updated` 를 적음, 목록 다시 만들기, 기록 한 줄. 한 답의 쓰기 여러 개는 차례로 (목록·기록이 섞이지 않게).
  있는 페이지는 `=== 덧붙이기`·`=== 고치기` 로 (아래 '있는 페이지 고치기'). 쓸 때마다 대화창에 `[위키 '이름']` 항목을 남김

명령: `/wiki` (상태), `init`, `use`, `off`, `ingest <raw/ 파일·폴더>`, `ask <질문>`, `save [제목]`, `lint`, `reindex`.

원본 (raw/):
- 대상 찾기: `raw/` 를 빼고 적거나, 이름이나 경로 끝만 적어도 됨 (파일은 .md 없이도). 맞는 것이 여러 개면 후보를 보여 주고 경로를 묻는다.
- 반영 여부: 페이지 머리말 `sources` 에 그 원본의 경로가 있으면 반영한 것. 폴더를 빼고 이름만 적은 것은 그 이름이 raw/ 안에 하나뿐일 때만 맞춘다 (같은 이름이 여러 폴더에 있으면 경로로만).
- 요약(source) 페이지 이름: 그 원본의 요약 페이지가 있으면 그 이름, 없으면 파일 이름. 같은 이름의 원본이 다른 폴더에도 있거나 다른 페이지가 그 이름을 쓰면 겹치지 않을 때까지 위 폴더 이름을 앞에 붙인다 (`2025 1월`, `회의록 2025 1월`). pi 가 정해 부탁에 적는다.
- 폴더째 반영: 그 폴더 아래 모든 깊이(숨김 폴더·`raw/assets/` 빼고)의 원본을 경로 순(마디마다, 숫자는 크기 순)으로. 이미 반영한 것, 글이 아닌 것(이름이 문서·그림·압축이거나 앞 4KB 에 0 바이트), 200KB 넘는 것은 뺀다.
  확인을 받은 뒤 원본 하나를 요청 하나로 보내고, `agent_settled` 에서 그 원본이 반영됐는지 보고 다음을 보낸다 (한 요청에 몰면 대화가 길어지고, 끊기면 어디까지 했는지 알기 어려움).
  한 번에 10개(`INGEST_LIMIT`). 멈추는 때: Esc·오류·답이 끝나지 않음(`agent_end` 의 마지막이 끝까지 쓴 답이 아님), 사용자가 직접 요청함, 원본 2개가 연달아 반영되지 않음. 같은 명령으로 남은 것부터 이어 간다.

hook: `session_start` (켜진 위키면 도구를 켬, 상태 줄. 폴더째 반영은 끝냄), `before_agent_start` (켜진 위키면 지침에 규칙 2~3줄: 세션 안에서 매번 같은 글이라 Copilot 대화를 새로 열지 않음), `message_end` (`/wiki save` 할 답 기억),
`input`·`agent_end`·`agent_settled` (폴더째 반영의 차례).

- 중계 서버 (tests/test_relay.py): `@tool wiki_write op=... title="한글 제목"` + 여러 줄 글 (내용의 `<` 그대로), 코드 블록 밖이면 다시 부탁

- 실제 pi 화면 (2026-10-21, 가짜 터미널 + 가짜 모델): 덧붙이기, 다시 쓰기 거절, `[위키]` 항목이 그 자리에 보이고 `-c` 로 다시 열어도 보임, 다음 요청의 대화 기록에 항목이 들어가지 않음

## 작업 방식 배우기 (2026-10-20)
에이전트의 지침·스킬을 실제 과제로 돌려 보며 다듬는 harness2(3ae3ae/harness2-cli, Apache-2.0) 를 검토했다.
그대로 넣지 않은 까닭은 세 가지다.
- 개선 단계에 Claude Code·Codex·OpenCode 중 하나가 꼭 있어야 한다 (폐쇄망에 없음).
- 과제 하나에 에이전트 실행 4번과 개선 세션 3번이 든다. 도구 한 번이 질문 한 번인 Copilot·사내AI 로는 과제 하나에 대략 100~400번이 들 것으로 봤다 (추정).
- 후보를 임시 git 폴더에서 따로 실행하므로 jupyter 모드와 맞지 않는다.

그래서 다시 실행해 비교하는 단계는 빼고, 생각만 가져왔다.
- 일하는 방식과 분야 지식을 나눠 본다. 분야 지식은 위키가 맡는다.
- 가장 가벼운 곳부터 고친다 (지침 한 줄).
- 한 과제에만 맞는 사실은 빼고, 고친 까닭을 짧게 남긴다.

정한 것:
- 위키를 쓸 때 같은 `wiki_write` 의 `=== 작업 방식` 부분으로 받는다. 따로 묻거나 도구를 한 번 더 부르면 질문이 한 번 더 들기 때문이다. 사람이 바로잡은 것, 되풀이한 실수, 오래 헤맨 까닭을 받는다.
- 자동으로 고치는 곳은 내 지침(`~/.pi/agent/AGENTS.md`)의 `<!-- kit lessons -->` 부분뿐이다. jupyter 모드에서도 PC 파일이라 중계 서버를 거치지 않는다.
  - 10줄·1200자까지다. 새 대화마다 첫 메시지에 들어가고, 사내AI 는 1만 자씩 나눠 보내기 때문이다.
  - 같은 줄은 횟수·날짜만 올린다. 넘치면 덜 쓰이고 오래된 줄부터 `lessons/archive.md` 로 뺀다.
  - 날짜 표시가 없는 줄(사람이 쓴 줄)은 건드리지 않는다.
- 스킬·이미 있는 규칙·프로젝트 지침을 바꾸는 것은 `=== 제안` 으로 받아 `lessons/proposals.md` 에 모은다. 사람이 보고 적용한다.
- 다음은 하지 않는다.
  - 원본 반영(ingest) 중에는 남기지 않는다. 폴더째 반영이 지침에 엉뚱한 줄을 쌓지 않게 하려는 것이다.
  - 이메일·전화번호·비밀로 보이는 줄은 남기지 않는다. 중계 서버가 `[이메일N]` 을 도구 인자에서 원래 주소로 되돌리므로 그대로 두면 지침에 실제 주소가 남는다.
  - UTF-8 이 아닌 지침 파일은 고치지 않는다.
- 고치기 전 지침은 `lessons/AGENTS.md.<때>` 에 10개까지 남긴다.
  - `/wiki lessons undo` 로 되돌린다.
  - 그 뒤에 사람이 지침을 고쳤으면 덮어쓰지 않는다 (`lessons/last.json` 에 적은 내용의 해시와 비교).
- 모드는 `wiki.json` 의 `lessons`: `auto` | `propose` | `off`. 없으면 위키의 `auto` 를 따른다 (write → auto, ask → propose).
  pi 안에서 `/wiki lessons on|propose|off` 로 바꾼다 (on = auto, 2026-10-20 사용자 제안). 위키가 켜져 있으면 지침 줄이 바뀌므로 Copilot·사내AI 는 다음 요청이 새 대화로 간다 (알림에 적음).
- pi 는 AGENTS.md 를 세션을 시작할 때와 `/reload` 때만 읽는다. 그래서 세션 도중에 고쳐도 지침 글이 바뀌지 않고, Copilot·사내AI 새 대화도 열리지 않는다. 반영은 다음 세션부터다.
- 시험(tests/test_wiki.mjs)에서 확인한 것:
  - 떼어 내기, 모드, 지침 줄;
  - 한도와 빼는 차례, 사람이 쓴 줄, 개인정보 거르기, UTF-8 아닌 파일;
  - 백업·되돌리기와 그 뒤에 바뀐 때, 파일이 없을 때;
  - 제안 모으기;
  - 확장의 `wiki_write` 처리: 페이지+작업 방식, 작업 방식만, ingest, 페이지 오류, propose, off.

## 있는 페이지 고치기 (2026-10-21)
있는 페이지를 고칠 때 모델이 페이지 전체를 다시 쓰게 했더니 위키 내용이 계속 사라졌다 (사용자 보고).
- `wiki_read` 는 여러 쪽을 합쳐 5500자까지만 주고, Copilot·사내AI 는 답도 길게 못 쓴다. 읽은 앞부분과 새로 안 것만으로 통째로 다시 쓰면 나머지가 지워진다.
- `auto: write` 로 알아서 남길 때는 검색 결과의 줄 몇 개만 보고 페이지를 다시 쓰기도 한다.

정한 것:
- 같은 `wiki_write` 의 `text` 안에 고치는 부분을 둔다 (도구를 늘리지 않음: 도구 설명이 길어지고, 페이지 쓰기와 한 번에 보내지 못하면 질문이 한 번 더 듦).
  - `=== 덧붙이기 <경로·[[제목]]> [## 절]`: 끝(또는 그 절 끝, 없는 절이면 끝에 만듦)에 붙임. 앞의 `--- sources: [...] ---` 는 페이지 sources 에 더함. 목록 뒤의 목록은 빈 줄 없이.
  - `=== 고치기 <경로·[[제목]]>`: `<<<<<<< 찾기` / `=======` / `>>>>>>> 바꾸기` 블록 (모델이 많이 본 찾아 바꾸기 형식. 표시 뒤의 말은 아무것이나).
    찾을 글은 한 곳에만 맞아야 하고, 그대로 없으면 줄마다 앞뒤 띄어쓰기를 무시하고 맞춘다. 하나라도 못 하면 그 페이지는 그대로 두고 오류.
  - 고친 뒤 머리말(title·summary·type)이 빠지면 쓰지 않는다. 줄바꿈이 CRLF 인 페이지는 CRLF 그대로.
- 통째로 다시 쓰기(`=== pages/...`)는 원래 본문의 줄 가운데 새 글에 없는 줄이 원래의 30% 를 넘고 본문이 70% 아래로 짧아지면 거절한다 (본문 300자 아래인 페이지는 보지 않음).
  말을 다듬거나 몇 곳 고친 것, 목록 표시만 바꾼 것은 막지 않는다. 나누기·정리로 일부러 줄일 때는 `=== 다시쓰기`. 고치기 전 페이지는 늘 `.history/` 에.

## 위키 항목 (2026-10-21)
작업 방식 배우기가 동작하는지 알 수 없다는 보고가 있었다. 알림(`ctx.ui.notify`)은 흐린 한 줄이고 세션을 다시 열면 없어지며, 도구 결과는 앞 10줄만 보여 '작업 방식' 줄이 접힌 쪽에 묻혔다.
- `wiki_write` 마다 `pi.appendEntry("pi-wiki", …)` 로 세션에 항목을 남기고 `registerEntryRenderer` 로 그린다 (확장 메시지와 같은 바탕색). custom 항목은 모델에게 가지 않는다.
  - 쓴 페이지와 방법(새로·덧붙임·고침·다시 씀), 쓰지 못한 것, 배운 줄 전체(`+` 더함, `=` 횟수만, `-` 한도로 뺌, `×` 거른 줄, 제안은 `?`), 지침 위치, 보기·되돌리기 명령.
  - 배울 때(켜짐·제안만, ingest 가 아님)인데 '작업 방식' 이 없었으면 `작업 방식: 이번에 배운 것 없음`. 그래서 배우기가 도는지, 모델이 적지 않는지를 나눠 볼 수 있다.
- 도구 실행 중에 남기므로 세션 파일에서는 도구 호출과 도구 결과 사이에 놓인다. 대화 기록을 만들 때 custom 항목은 빠지므로 모델이 받는 순서는 그대로다 (실제 pi 로 확인).
- pi 화면(`ctx.mode === "tui"`)이 아니면 예전처럼 배운 것이 있을 때만 알림.
